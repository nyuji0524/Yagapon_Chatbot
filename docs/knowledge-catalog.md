# 用語・人名カタログ

矢実固有の用語、略語、システム名、企画名と、確認済みの人名を管理者確認前の候補として一括生成する。
AIの出力をそのまま正式情報にはせず、すべて `candidate` から始める。

## 一括生成

```bash
python -m knowledge_catalog \
  --root /path/to/YagamiFes-IT-Knowledge \
  --guild-id 1299324210069504082 \
  --output data/knowledge-catalog.json \
  --csv data/knowledge-catalog.csv
```

標準では、精選済みナレッジ、役職資料、年度概要・教訓・プロジェクト・決定・資料、会議原文を対象にする。
月次ダイジェストは一次情報の再掲が多いため除外する。必要な場合だけ `--include-monthly` を付ける。
文書は認証情報らしい文字列をマスクしてからAIへ送る。
既定ではFlash-Liteで2回抽出して結果を統合し、抽出の揺れによる見落としを減らす。
費用を優先する場合は `--passes 1`、網羅性をさらに確認する場合は最大5まで指定できる。

人名は、Discordアーカイブの `people/name-map.json` にある確認済み氏名を優先する。
本文から役職、所属、ハンドルネームと本名の関係を推測して確定しない。

## 保存と再生成

- JSONが正本で、CSVは確認用の派生出力。
- 各項目は安定ID、種別、状態、revision、根拠文書、確信度を持つ。
- 状態は `candidate`、`approved`、`rejected` の3種類。
- 管理者が一度でも編集した項目、承認・却下した項目は再生成で上書きしない。
- 未編集の候補だけ、再生成時に根拠と説明を更新する。
- `data/` はGit管理外。人名を含む実データを公開リポジトリへコミットしない。

CLIとAPIを同時に書き込む運用は避ける。将来管理画面から再抽出を起動する場合は、ジョブ単位の排他制御を追加する。

## 管理画面向けAPI

全APIで `Authorization: Bearer <YAGAPON_API_TOKEN>` が必要。

| 操作 | API |
|---|---|
| 一覧・検索 | `GET /admin/catalog?guild_id=...&kind=term&status=candidate&query=...` |
| 手動追加 | `POST /admin/catalog` |
| 編集・承認・却下 | `PATCH /admin/catalog/{id}?guild_id=...` |

更新には現在の `expected_revision` を渡す。別画面で先に更新されていた場合は `409 Conflict` を返すため、画面側で再読込して競合を解決する。

用語を `approved` にすると、既存のサーバー別語録へ同期し、RAG回答、文字起こし、議事録で利用できる。
人名は誤同定の影響が大きいため、承認しても既存メンバー情報へ自動同期しない。

## 管理画面の推奨フロー

1. `candidate` を用語・人名で分け、確信度と根拠文書を並べる。
2. 「意味未確認」を優先表示し、人が説明、読み、別名を補う。
3. 根拠抜粋と元文書の場所を確認して、承認または却下する。
4. 承認済み項目も検索・再編集できるようにする。
5. 人名はDiscord ID、確認根拠、別名を見せるが、不要な個人情報は表示しない。
