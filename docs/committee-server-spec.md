# 28th全体サーバー仕様・実装状況

最終更新: 2026-10-28

この文書を、28th矢上祭実行委員会Discord（以下「全体サーバー」）における委員登録、
役職申告、鍵管理、Yaga Support連携の基準仕様とする。構想と稼働中の機能を混同しないよう、
各項目に実装状況を記載する。

## 1. 目的と原則

- 委員が自分で所属局・学年を登録し、Discord上で必要な場所へアクセスできるようにする。
- 慶應メールを確認し、Yaga Supportの`users`・`staffInfos`との照合結果を記録する。
- 企画長・役員の申告は承認制とし、DiscordとYaga Supportの両方から処理できるようにする。
- Discordの自己申告値だけでYaga Supportの権限を確定しない。Functionsが信頼できる保存値を照合する。
- 鍵の所持者と操作履歴を再起動後も保持し、返却・差し替え忘れを減らす。
- `/committee_setup`はロールと操作パネルだけを冪等に整備する。カテゴリ・チャンネルは一斉作成しない。

## 2. ロール

### 所属局

`IT局`、`総務局`、`装飾局`、`ステージ局`、`屋外局`、`室内局`、`広報局`、`渉外局`

選択UIでは各局の色に対応するハート絵文字を表示する。通常の委員は所属局を1つだけ持つ。

### 学年

`１年生`、`２年生`、`３年生`（全角数字）

### 役職・管理

- `企画長`
- `役員`
- `副局長`
- `局長`
- `執行部`
- `サーバー管理者`

`企画長`と`副局長`または`局長`は兼任できる。副局長と局長は同時に成立しない。
副局長・局長の承認時は、個別役職に加えて`役員`も付与する。
`一般委員`、`28th委員`は使用せず、既存ユーザーの役職承認時には除去する。

`/committee_setup`実行者には、テスト・復旧を行える`サーバー管理者`を付与する。
このロールはDiscord Administrator権限を持つため、実行コマンド自体も管理者限定とする。

## 3. 委員登録フロー

1. 本人がDiscordのサーバープロフィールから表示名を変更する。Botは表示名を変更しない。
2. `#ロール選択`で所属局と学年を選ぶ。選び直した場合は同じ種類の旧ロールを置換する。
3. 「登録を完了」を押し、慶應メールアドレスを入力する。
4. Firebase Functionsが確認コードをメール送信する。
5. 本人がDMで確認コードを入力する。
6. FunctionsがメールをキーにYaga Supportの`users`と`staffInfos`を照合する。
7. Discord側は照合結果（UID、users存在、staffInfo存在）を保存する。
8. usersに未登録でもDiscord側の局・学年登録は完了させ、完了DMでYaga Supportの導入先と
   現在のサーバー表示名を案内する。
9. 局・学年の変更案は`committeeStaffInfoChanges`へ保存し、`staffInfos`正本へ直接書き込まない。

メール確認前でも局・学年ロールは選択できるが、企画長・役員申告は登録完了後だけ利用できる。

## 4. 企画長・役員申告

### 企画長

- 登録済みの所属局（department）に属するFirebase上のorganizationを候補表示する。
- 候補には「この中にない」を必ず含める。新企画、データ誤り、他人の誤申告は手動対応へ回す。
- 承認後に`企画長`を付与する。役員との兼任を妨げない。

### 役員

- 本人は`副局長`または`局長`を申告する。
- 承認後に`役員`と選択した役職を付与する。
- Discordの申請メッセージまたはYaga Supportの管理画面から承認・却下できる。
- Functionsを正本とし、Discord側は処理結果を同期する。二重処理は冪等に扱う。

### 通知

おしらせやがぽんへの申請通知には、役職、局、学年、Discord ID、Yaga Support照合状態、
申請状態を含める。局カラーのEmbedで表示し、既存通知形式とは後方互換にする。

## 6. 鍵管理

### 対象と操作

対象は`日吉部室`、`矢上部室（212）`、`矢上部室（209）`、`地下倉庫`、`屋外倉庫`。

- `あけ`: 借りた人を現在の所持者として記録する。
- `しめ`: 現在の所持者が返却済みにする。
- `さしかえ`: 現在の所持者から選択した受取人へ所持記録を移す。

状態、操作履歴、未送信通知、209申請はSQLiteへ保存する。`#鍵管理状況`は固定メッセージを更新し、
`#報告`の操作通知は既定で5分後に削除する。送信失敗した履歴は未送信のまま残し再送する。

### 矢上部室の局間差し替え禁止

矢上部室（209・212）は、**最初に借りた局の委員にだけ差し替えできる**。

- `あけ`時に、本人の局ロールを貸出元局として保存する。
- `さしかえ`時に、保存済みの貸出元局と受取人の局ロールが一致することを検証する。
- 局ロールが0個または複数で一意に決まらない場合は差し替えを拒否する。
- 局をまたいで渡す場合は、一度`しめ`を行い、新しい局の人が改めて`あけ`を行う。
- 旧レコードに貸出元局がない場合は、現在の所持者の局を一度だけ採用して保存する。
- 日吉部室・地下倉庫・屋外倉庫にはこの制限を適用しない。

操作通知には局を表示する。矢上部室では保存した貸出元局を優先し、それ以外は操作対象者の
現在の局ロールを表示する。不要な局ロール通知を発生させないため、局はメンションせず文字列で表示する。

### 209の追加確認

- 渉外局、執行部、Administratorは通常操作できる。
- それ以外の委員が借用する場合は、理由を入力して`#209利用申請`へ送る。
- 渉外局または執行部が承認・却下し、誰が処理したかを残す。
- 209の差し替えは、この承認条件に加えて上記の同局制限も満たす必要がある。

## 7. 信頼境界と権限

- Discordの局・学年選択は自己申告であり、Yaga Supportの管理権限の根拠にはしない。
- メール確認、users/staffInfos照合、役職申請の保存・確定はFirebase Functionsで行う。
- `staffInfos`正本は自動更新せず、差分案を`committeeStaffInfoChanges`へ保存して確認可能にする。
- 現行Yaga Supportとの互換性のため、承認済み役職は`users.roles`にも反映する。
- サーバー管理操作、強制返却、セットアップはDiscord Administratorに限定する。
- 209承認は渉外局・執行部・Administratorに限定する。

## 9. 残タスクとリリース順

1. この変更の鍵管理テストを通し、PRをレビュー・マージしてBotへデプロイする。
2. Discordテストサーバーで、209・212の同局差し替え成功、局間拒否、209承認、局表示を確認する。
3. Firebase PR #64をレビューする。承認後にマージし、Functionsをデプロイする。
4. Resendの送信元ドメイン、APIキー、確認コードの有効期限・再送制限・レート制限を本番値で確認する。
5. Yaga Support PR #117をFunctions反映後にマージし、Firebase Hostingへデプロイする。
6. notifier PR #7をリポジトリ管理者がレビュー・マージ・デプロイする。
7. Emulatorで、登録、未登録ユーザー、staffInfo不一致、企画長候補なし、兼任、二重承認を再確認する。
8. 本番テスト用アカウントで、メール送信からDiscord/Yaga Support双方の承認までE2E確認する。
9. `committeeStaffInfoChanges`の確認・適用・却下・監査・滞留通知に関する運用責任者を決める。
10. 手動作成したチャンネルの閲覧権限、固定案内、フォーラムタグ、局間28組を権限監査する。

本番切替時は、Functions、Yaga Support、notifierの順序を崩さず、旧`isAdmin`・`users.roles`互換を
確認してから委員へ案内する。
